# 核心优化评估

本文件保留评估时的发现；本轮已实施前四项，当前实现和验证边界见 [核心优化实施](核心优化实施.md)。背光/HBM 缓存仍待实测。

评估日期：2026-09-29。对象为 LumaCurve 当前生产 highlevel C 目标的 35 个源文件。本次为源码审查，没有修改引擎、安装包或配置默认值，没有进行 Android CPU、耗电和响应延迟实测。

当前核心已有动态采样、事件等待、温控和电池缓存、亮度变化门槛与读回冲突保护。优化应先减少系统命令与恢复适配层的开销，再考虑改变响应策略；不能给出未经测量的省电百分比。

## 与优化一起处理的可靠性问题

1. `refresh_settings.c` 用 atoi 读取模式，`"null"` 或其他非数字文本会变成 0 并通过模式校验；滑块 strtol 没检查结束指针，也会把非数字结果当成 0。需要严格解析、检查命令返回，并在失败时保留最后有效值，避免误认手动模式或零滑块。不能只合并命令却延续这个问题。
2. `write_state_file.c:242–245` 没有检查各字段写入和 fclose 的失败结果，就执行 rename；写入失败可能发布不完整快照。需要失败不替换旧帧、明确记录错误，并保持临时文件清理可控。
3. 当前状态发布并非纯观测：它调用电池刷新两次，还可能清除到期的 external_write_hold。提高快照频率前必须把这些业务变化放回主循环，否则看 WebUI 可能改变状态演进。
4. 状态协议里的 `version` 仍写 2.5.5，而模块版本为 0.0.1。可拆成模块版本与恢复来源版本，不能让维护工具混淆二者。此项是元数据一致性，不是性能问题。

## 已有优化，不应重复或贸然取消

- main_business.c:2103–2178 已按状态切换约 250ms、1000ms、3000ms 的光感速率；主循环、背光帧和采样不是同一个周期。
- 空闲 NDK 路径使用 ALooper_pollOnce 等待；背光过渡另按执行帧调度，不是一直忙轮询。
- refresh_battery_state.c 已有 15 秒缓存。
- business_thermal.c:51–65 已按条件选择 15/10/5 秒读温度，发现结果也有缓存，不是每帧遍历所有温控目录。
- refresh_power_wakefulness 与 refresh_display_state_on_edge 在所审主循环位置是亮屏边沿调用，不能当成每帧 dumpsys 来估算收益。
- 小变化确认、方向反转等待、唤醒只读、外部写入冲突和极端温控都有实际保护意义，不以省电为由直接删掉。

## 实施和验收顺序

1. 保留当前安装包和引擎基线，迁入针对 LumaCurve 源码的核心回放入口。当前 tests 主要是 WebUI、安装器、打包与独立构建，尚不能证明改算法后行为正确。
2. 先记录一轮循环耗时、settings 刷新耗时/次数、NDK 获取次数、背光/HBM 读写次数、状态序列化时间和发布次数。统计应低频汇总，避免日志本身影响采样。
3. 第一批实现严格设置解析、状态写失败处理、生产格式化与状态访问优化；以旧 LumaCurve 为行为参照，验证目标背光、保护状态和状态文本。针对原来的错误输入，明确记录有意修正的差异。
4. 第二批处理设置命令合并与传感器批量读取；分别增加命令失败、部分缺失、突发事件、乱序时间戳、接近事件、连续无效样本、读取失败场景。
5. 状态订阅单独作为观测功能改动验证：订阅到期必须恢复低频；息屏不能强行唤醒传感器；前端轮询间隔与后端发布时间分别说明。
6. 实机覆盖暗室、室内、户外强光、快速出入明暗、反复锁屏、手动滑块、充电高温、模式切换、配置重载和异常退出，再比较耗电与响应。没有设备测量时，只报告源码层面的开销减少，不宣称总体省电。

verify_project.py 的 `--upstream` 当前只允许恢复工程的品牌和路径变化。开始修改核心后，应把“品牌改名仍完全相同”和“二开算法回归通过”分成不同验证阶段，不应删掉断言后继续宣称原 ELF exact match。
