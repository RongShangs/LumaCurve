# 室内稳定与硬件可靠性优化

本文记录上一轮实现。当前时域与双光感策略已扩展，现行说明见 [iOS 亮度研究与双光感场景自适应](iOS亮度研究与双光感场景自适应.md)，以下 100 lux 限定不再适用于当前版本。

日期：2026-09-29。模块仍为 0.0.1 / 00001，保留 GPL-3.0，仅本地开发与打包。

## 本轮界面

顶栏下角与底栏上角的圆角半径从 12px 调为 18px，方向保持不变。状态标题与说明移到手机图形下方，详细读数按钮位于标题左侧；更新时间仍在背光刻度下方。状态页保持固定布局，详细数据在弹窗中滚动。

## 从日志能判断什么

用户日志同时出现照度突变、约八秒的光感事件过期，以及密集的 external brightness sync。后者表示主循环读到的硬件亮度与最近记住的亮度相差超过 64 个硬件单位，可能来自系统自动亮度、厂商显示服务、其他调光软件，或驱动返回值变化。日志不能单独识别写入者，也不能证明全由曲线灵敏度引起。

本轮不移除外部同步、让渡窗口和权限判断。室内稳定针对引擎自己的普通目标波动，无法约束其他服务正在写入的亮度。实际仍频繁 external_sync 时，应结合 brightness_owner、write_governor_reason、last_write_result、last_write_readback、write_readback_mismatch_streak 和有效光感年龄继续定位。

## 室内时域策略

配置新增 indoor_stability=1，默认启用，设置页「日常调节」可以关闭。缺失该键的旧配置在新进程中使用默认开启；配置重载时省略该键保留当前选择。配置格式版本维持 11；新增项可选，未知项仍保留。

策略接在保护计算之后、原目标防抖之前：

1. 只处理 daemon 拥有控制权、非亮屏只读观察、有效且未过期的照度样本，平滑照度为 0–100 lux。
2. 不超过已接纳目标 5% 的变化保持目标，门槛至少为配置中的 min_step。死区参考目标亮度，不参考当前正在过渡的亮度。
3. 普通变化最多保留七次不同有效光感事件的目标值，取中位数；同方向至少三次新事件，并持续变亮 3 秒或变暗 4 秒后，交给原目标防抖接纳。
4. 方向反转、目标锚点改变、时钟倒退或超过六秒的事件间隙会清空确认。重复轮询同一事件不累计样本，也不单靠墙钟等待完成确认。
5. 超过目标 50% 的明显变化沿用原路径；阳光、硬温控、可信突暗、暗降窗口、原有唤醒/低照度确认快速路径均绕过新增确认。

这些时长与门槛是本轮保守起始值，不是机型校准结果。新增确认后仍有原来的防抖等待，因此小幅趋势通常需要比 3–4 秒更久才产生实际调整。关闭开关可恢复原目标确认策略，便于同设备对比。

## 四处核心处理

| 项目 | 现在的行为 |
|---|---|
| sysfs 光感 | 拒绝非有限值、负值、超过 200000 lux 的样本。初始化时钟输出并检查失败、纳秒范围与换算溢出；失败返回无新读数，不更新有效性和新鲜时间。 |
| NDK 启用 | 只有 enableSensor 返回 0 才认为启用成功。前置失败不会标记就绪；后置单独成功可提供 NDK 光感。启用成功仍不等于有有效事件。恢复启用失败时不伪装为传感器已开启。 |
| 屏幕状态 | 节点只接受正常关闭且值为 0–4 的读取；失败尝试两秒限时的系统电源查询，同类失败五秒内不重复拉起命令。查询失败保留最近可信状态；冷启动未知时不接管亮度。内部未知与熄屏是不同状态，既有 bool 接口返回 false 表示未确认亮屏。 |
| 背光路径 | 安装与引擎共用同一个 C 发现策略：原节点有效则优先保留，否则在有界扫描中只接受唯一有效 brightness/max_brightness 对。全部亮度读写、chmod、最大值、屏幕节点和同目录 HBM 候选一起切换。歧义或缺失时退出，不猜测。 |

NDK 返回值语义参考 [Android NDK Sensor 官方文档](https://developer.android.com/ndk/reference/group/sensor)。屏幕回退只识别明确的 Awake、Asleep、Dozing；不把未知输出或默认初始化字符串当成实测。

控制、服务、卸载与诊断脚本使用相同选择规则的 shell 实现；安装探测与运行端独立重新检查，不使用可能跨重启失效的检测报告作为运行路径。发现只读节点不表示实际写入一定成功，执行器继续检查写入与读回。

## 验证边界

tests/core_reliability.py 编译生产 C，测试异常浮点/时钟、屏幕缓存和限频、唯一与歧义背光、前后启用组合/恢复失败、室内抖动与持续趋势、配置严格解析和回滚。另编译四个独立错误变体，必须出现语义断言失败。

tests/core_main_replay.py 用哈希固定的旧 C 回放 37 个场景：关闭室内稳定后，前置缺失而后置可用的场景是明确的修正，其余场景要求完整记录一致。另用默认开启配置回放相同场景，检查目标范围，并对保护/所有权相关场景要求完整控制记录保持一致；室内抖动场景双侧实跑比较实际背光写入。

报告位于 docs/validation。以上是主机上的受控 IO 回归，不能替代 Android 实机上的连续事件、功耗、厂商服务竞争和实际背光写入验证。尚未发布 GitHub。

本轮结果：35 项浏览器检查、16 项安装器检查、13 项工程检查通过；37 项旧配置回放中 36 项完整记录一致，1 项后置单独可用按明确修正通过。默认开启的 37 项场景与 1 项室内专项通过；室内专项 400 次等待中实际背光写入从 7 次降至 6 次，此数字仅适用于该受控输入，不代表实机改善比例。原核心与新增可靠性各四组语义负向均成功检出错误变体。
