# 核心优化实施与验收

基线为本地提交 `abe393e05a71831cd86abe9062ffa50d90991b7c`，版本继续使用 0.0.1 / 00001。旧安装包、源码包与核心源码保存在 build/history/pre-core-optimization-*，不覆盖旧快照。没有推送或发布 GitHub。

## 实现

1. **设置读取**：原三次 popen 合并为一次 shell 会话，仍执行同样的三个 settings 查询，保留原用户选择语义。并非减少为一次 Android settings 服务调用。完整校验 mode 的 0/1、浮点范围与有限性、整数尾部和溢出；非零退出、缺失、过长或格式异常不再变成有效零。命令失败不提交部分结果；成功命令中的无效字段保留其上次有效缓存，记录 settings_read_failed。原 2 秒元数据检查、60 秒缓存策略和 users/0 监视路径保留。
2. **状态序列化**：统一写入 16 KiB 栈缓冲区，用类型明确的原生格式化替代逐字段恢复层分配。完整格式化后只调用一次 fwrite。溢出、打开失败、短写、关闭失败或 rename 失败均不替换上一份完整状态。字段、顺序、符号和小数位与基线相同。
3. **纯观察快照**：序列化函数不刷新电池、不清理业务标志。原控制发布入口保留一次带缓存的电池刷新，观察入口直接调用纯序列化，不改变控制状态。
4. **状态订阅**：可见状态页在既有读取命令中用 shell 内置重定向续约 `/data/local/tmp/luma_curve_ui_watch`。守护进程每秒至多检查一次订阅文件，离页、后台或关闭后约 4–5 秒到期。亮屏且订阅有效时，新快照按 1 秒节流；较长 usleep 可拆分为纯观察等待，但控制循环仍等待原总时长，不提前采样或操作执行器。息屏与无订阅保留原低频发布。
5. **NDK 批量**：每次请求剩余事件数，总量仍限制 16；按原顺序处理，继续验证有限值、照度范围、前后光感各自时间戳、接近事件与无效计数。

NDK 阻塞等待保持原超时，因此新快照发布也可能等待下一个控制边界，稳定模式下间隔可达约 3 秒。页面每秒读取与传感器实际样本更新是两个频率；不把旧样本伪装成新采样。背光节点/HBM 缓存和曲线参数本轮不改，耗电收益待实机测量。

## 验证

- `tests/core_optimization.py --negative`：生产 C 边界模拟测试；10 组设置输入/退出/缓存，200 组传感器旧实现双侧全状态比较，100 组状态文本逐字节比较，容量与四类 IO 故障，以及订阅刷新、限频、到期、息屏和等待总时长。
- 四份独立破坏版必须正常编译，然后因语义断言失败被检出：放松设置解析、接纳重复时间戳、忽略短写、订阅不按时到期。生产文件不被修改。
- `tests/core_main_replay.py`：与固定旧 LumaCurve C 基线双侧完整主循环回放，37 场景覆盖阳光/HBM、温控、学习、模式、唤醒、外部写入、NDK 缺失/无效/空窗、背光故障、信号回调和退出。比较每个控制等待边界、全业务状态、文件、日志和权限；仅规范化有意合并的 settings 命令，并从比较中去除有意改变的 NDK 请求分组。该主循环回放未启用 UI 订阅；订阅通过生产 helper 和 WebUI 桥测试验收。
- 旧 C 文件通过 manifest 的 SHA-256 固定；新验证报告绑定当前源码哈希。verify_project 同时要求四项负向通过和 37 场景全部通过，旧报告不能验证新源码。
- 原 ARM64 ELF 和已恢复的测试框架用于主循环回放的符号与 IO 测试基础，不是本轮对原 ELF 的三侧差分。没有宣称 Android 实机性能、完整订阅集成或 OS 级信号已验收。
- 核心 helper 测试仅需 Windows GCC；完整主循环回放额外依赖恢复工程的测试框架及分析 Python 库。这些不是源码独立构建依赖；源码仍可用 Python + NDK 或 CMake + NDK 独立构建。

执行步骤见开发说明，报告位于 docs/validation；交付哈希在 dist/delivery-manifest.json 和 dist/SHA256SUMS.txt。
