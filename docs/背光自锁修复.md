# 背光自锁：设备证据与 test03 修复

2026-09-29，手机 root Agent 在 Enforcing 下完成四组对照：运行时主屏节点
0444，暂停后恢复 0644；0644 下写回当前值和增加 1 均成功；先持有写 FD 再改
0444 仍可写，而 0444 下重新打开失败；恢复原运行状态后故障复现。
因此本机驱动有写接口，先前“驱动只读”的结论不成立。

旧核心接管执行 chmod 0444，执行器每帧 open/write/close，造成 kernfs 打开时
拒绝新写句柄。安装阶段节点可写，运行接管后自锁，也解释了前后探测不一致。

test03 在生产 libc 边界管理背光资源：先恢复 0644，open(O_WRONLY|O_CLOEXEC)，
成功后 chmod 0444 并持有 FD。业务每帧的 open/close 是对持有 FD 的逻辑借用，
实际 write 前 lseek(0)；启动重复接管不增加 FD。熄屏、手动模式、观察窗、退出
的既有释放调用恢复权限并关闭 FD。打开或上锁失败回滚，不宣称接管成功。
进程异常死亡后的遗留 0444 在下一次接管前恢复。

实际写失败后核心恢复 0644、关闭 FD、取消过渡，owner 标为
write_failed_passthrough，daemon_can_write 为 0，保留 errno 和失败阶段。
暂不自动抢回控制权，排查后重启引擎或重新切换自动模式。
持有 FD 不保证所有系统亮度通道都被阻止；原有读回冲突检测继续生效。

安装探测写回当前背光值，要求 write 完整、close 成功且读回一致。
actual_brightness_write=unverified 不能再通过安装检查。
探测不改变自动模式，不打开 HBM，不另设亮度值；若系统并发改值导致读回不同，
保守判失败，需暂停冲突写入后重试。热测试先暂停旧核心再探测，避免撞上其 0444。

验证分层：backlight_ownership.py 在 kernfs 行为模型中验证 1000 次持有 FD 写入、
50 次释放/重接管、失败回滚及偏移重置；恢复旧每帧 close 的负向必须失败。
android_actuator.py 使用实际 ARM64 ELF，并模拟 0444 禁止新打开的权限行为，
验证 sysfs 与 NDK 传感器路径能实际调用写入与读回，写失败释放控制权。
这些是主机仿真，修复后的硬件持续控制仍需手机 Agent 验收。

设备验收：先恢复温和曲线；核对 core_build=20260929-test03；观察成功计数递增、
stage=readback_ok、目标与实际逐渐接近；检查 /proc/PID/fd 有主屏写 FD；
切手动/熄屏/暂停后确认 FD 关闭、权限恢复，再回自动验证重新接管。
若仍被系统覆盖，记录 readback_mismatch 和实际节点值，不以运行状态代替写入证据。
