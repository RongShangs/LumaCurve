# K90 Pro Max：息屏唤醒卡死专项排查

2026-10-10；诊断增强构建 `release-2.4.0-r14 / 24014`，沿用正式签名和现有亮度需求。

## 已取得的证据

用户补充本批反馈均为 K90 Pro Max：常在息屏后刚唤醒或解锁时卡住，持续亮屏使用没有出现；部分伴随状态栏消失、音量键失效，可能数分钟后恢复。此为反馈描述，不是已完成的复现。之前 mi15 的指纹反馈另行记录。

收到的分析包由 `myron / 25102RKBEC / OS4.0.0.33.XPMCNXM` 导出。包内 APK 版本为 **2.3.1 / 23106**，Hook 为 **release-2.3.1**；不能沿用“应该是 2.4.0”的口头估计。设备实际使用 `physical_mapping` 传统映射链路，与当前 USB 手机的 Refactor 链路不同。

包内暗光锁定关闭、模块无光感订阅；手动面板功能可用但没有接管，输出所有权为 none。持久手动记忆、暗光稳定、户外增强与部分显示温控调整开启。这是恢复后的快照，不能证明故障发生前所有开关、所有权也完全一致。

## 时间线

时间取自包内 LSPosed 记录，均为设备当地时间：

| 时间 | 可确认的事件 |
| --- | --- |
| 约 12:19 | 用户称此时开始卡住，尚无同时刻线程栈 |
| 12:20:12–12:20:29 | 原 system_server（829）的显示线程仍输出 Doze、ScreenOff 等路径切换记录 |
| 12:20:26 | 另一个定位模块出现重复注册 Hook 达 64 次的异常；仅是并发环境证据，不能直接认定冲突或根因 |
| 12:20:52 | 原系统进程仍有其他模块记录，之后存在约 111 秒日志缺口 |
| 12:22:43 | 新 system_server（19080）启动并重新加载模块，HyperLux 标识仍是 release-2.3.1 |
| 12:22:47 起 | 传统曲线重新连接；随后出现恢复后的曲线计算和手动亮度调整 |

导出时系统 uptime 约 250200 秒，而新系统进程才启动约一分钟。结合两组 PID 的加载记录，可确认期间发生过 **system_server 进程重启**，不是一次整机冷启动。现有材料不能区分由 Watchdog、崩溃、外部终止等哪一种机制触发。

两份 display dump 都采于恢复之后，显示 ON/BRIGHT、自动亮度启用，不能把它们当作卡住时的线程或显示状态。原分析包的过滤显示日志为空，没有 crash 缓冲、Watchdog/ANR 线程栈，因此尚不能定位造成系统进程重启的代码行。

## 已修复风险与机型核对

对照本地 v2.3.1 源码，旧版会在曲线采样回调内发布诊断，并直接发起 OEM 重算。当前版已将这两者排队、合并并防重入；屏幕切换回调先设置内存退让标记，再排队清理，且注册表锁内不再调用 OEM getter 或关闭运行时。详见 [息屏稳定性审查](2.4.0-unlock-stability-20261010.md)。

本次包内传统链路固件接口检查 **59 项通过**。核对显示：`DisplayPowerController.updateBrightness()` 自身只排队；`DisplayPowerControllerImpl.updateAutoBrightness()` 会同步进入自动亮度更新。两条方法不能混称为同步重算。当前的防重入修复覆盖共同入口，但没有故障栈，不能据此宣称已证明或彻底修复 K90 的偶发卡死。

## r14 诊断增强

分析包优先收集 crash 缓冲、系统故障标签、进程启动/死亡事件，以及最近三天的 system_server Watchdog、崩溃、ANR 和系统应用崩溃/ANR DropBox 记录，随后再收集显示快照和私有固件。这样可减少耗时快照挤掉短期故障证据的机会。

只在用户导出分析包时读取；无常驻故障轮询、无线程信号注入、不清空日志、不强制重启系统服务。每条命令最多六秒，DropBox 客户端另有四秒超时；仍受原总时限和每条输出 2 MiB 上限约束，超时/截断/不可用均记入 manifest。记录可能包含系统应用错误，分析包仍属于私有诊断材料，不进入公开交付。

## 重启后的日志是否保留

- 已导出的 ZIP 是磁盘文件，重启后仍可发送。
- 整机重启通常会丢失普通 logcat；模块内存中的曲线、输出和日志历史在系统进程重启后也重新开始。
- LSPosed 磁盘日志与系统 DropBox 可能跨进程或整机重启保留，但有容量、保留期及厂商差异，不保证存在。
- 本次分析包就保留了系统进程重启前后的 LSPosed 记录，所以“重启后抓包一定没有用”并不成立。

建议发生后先恢复可操作状态，尽快导出分析包，避免反复重启和清理日志。同时写明发生时间、精确安装版本、是否从 AOD/息屏唤醒及是否使用指纹。不能为保留日志要求用户让手机持续卡住。

## 验证范围

主机验证覆盖输出截断和总时间预算耗尽后跳过故障命令；真实 Android 的命令可用性、归档完整性另做设备检查。已连接设备不是 K90 Pro Max，不将其息屏循环或日志导出成功当作 K90 偶发卡死已经解决。


收尾验证：诊断主机60项、布局5191项通过；已连接 pandora 上生产导出8项fault记录均成功、ZIP CRC完整且配置不变。最后仅界面间距修订，最终实装APK另校验一致；两个APK的测试范围与哈希在交付build-info中分别记录。给K90用户的操作见 [排查包使用说明](2.4.0-k90-user-guide-20261010.md)。
