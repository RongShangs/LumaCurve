# r17：显示线程中的状态写入隔离

2026-10-10，`internal-2.4.0-r17 / 24017`，未发布内部测试版。

## 为什么做

r16 只修复故障取证，不能描述为解决 K90PM 卡死的版本。此前 r12/r13 已调整息屏清理、重算、防重入和监听清理，但最新 r15 仍复现，说明不能宣称那些改动已解决该故障。

继续审阅发现，`HookRuntime.publishAcknowledgement()` 与 `publish()` 在系统显示 Handler 上同步调用 `Settings.Global.putString`，包括配置确认与多份状态分片。即使这些调用不在原始亮度计算栈内，设置服务阻塞仍会让同一显示线程等待，影响后续显示任务。这是能够从本地代码确认的阻塞风险，尚不是现场死锁栈证实的 K90 根因。

## 实际改动

- 配置确认和状态快照在原显示线程生成，保持原有字段含义；只将其写入设置服务的操作交给单独的 `HyperLux-state-io` 线程。后台线程不读取 OEM 亮度对象、不调用亮度控制或注册传感器。
- 每个运行实例最多保留一个待写确认和一个待写状态。更新密集时整份替换较旧的待写快照，不让任务无限堆积，也不混合不同快照的分片。
- 写入保持原顺序：分片在前，核心清单在后。失败时不提交该批后续内容，未来正常更新可再次写入；没有忙等或失败重试循环。
- 实例关闭时清除待写状态，并停止当前批后续写入；已经进入设置服务的单次调用无法强行撤销。全进程串行写入，旧实例尚未返回的调用不会跑到新实例任务之后。
- 其他控制操作不变：曲线应用、模式切换、记忆保存和配置读取仍保持原流程。此轮不是将所有系统服务访问异步化，不能排除其他阻塞来源。

## 验证及限制

生产类在主机上进行了 21 项测试：真实阻塞写入期间调用方仍能提交、上万次更新合并到最新状态、分片顺序、外部可变 Map 隔离、写入拒绝和异常恢复、关闭时丢弃剩余批次。既有清理恢复测试 100 项通过。完整 Android 编译、全量构建、原签名和归档一致性按本构建单独核对。

这是直接减少显示线程阻塞的预防性修复，不是已经验证解决 K90PM 偶发卡死。未要求故障用户重复复现，未安装、重启或操作连接手机；不继承 r15 的真机结果。线程空闲时没有轮询，不改变光感采样率和用户配置。
