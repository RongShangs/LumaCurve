# 2.4.0 息屏与指纹解锁卡死风险排查

修订构建：`release-2.4.0-r12 / 24012`。保留 2.4.0 需求、配置格式、曲线、场景条件及签名。

## 反馈与证据边界

截图中有用户反馈：停用模块后不再卡屏；另有 mi15 用户反馈息屏后指纹盲解必现，卸载后恢复。另一个机型仅写作“90pm”，不据此推定完整型号。作者估计反馈版本为 2.4.0，但尚无精确构建、系统版本、功能开关、ANR、watchdog、线程堆栈或分析包。

以下是代码中可以确认的调用风险，并非已从故障设备证明的死锁根因。当前 ADB 无设备，不能宣称已在上述机型复现或解决。

## 风险与修改

1. `RawPanelOutputHooks.setScreenState` 的前置回调原先同步执行 `screenOff`；即使没有接管亮度，`relinquish` 也会调用 Settings.Global 写入空的所有权标记。暗光锁定持有模式时还会读取和恢复自动亮度，手动节点模式会写原生租约。这些操作可能延长系统的亮灭屏调用，甚至与系统锁发生交互。

   现在前置回调只设置内存中的退出屏幕标记、合并投递清理任务；立即允许系统输出，不等待设置提供者。清理在原显示线程下一轮消息中执行。等待清理期间不允许暗光锁定重新进入，也不接受依赖亮屏状态的新接管；快速息屏再亮屏会先完成旧会话清理。停止/关闭时撤销待执行任务。未持有亮度所有权时不再重复写清除标记；启动时的持久标记恢复仍保留。

2. `HookRuntime.sample` 在 OEM 曲线计算的后置回调内同步 `publish`，其中包含 Settings 确认和状态写入、显示亮度/锁屏状态诊断及序列化。

   现在采样只更新显示线程的数值和计数，再合并投递状态发布；首个有效采样及时发布，其余维持既有节流。非显示线程及无效采样不更新共享诊断数据。

3. 户外策略、记忆恢复等路径调用 `requestRecalculation` 时，原先会在当前 OEM 计算尚未返回前再次调用 OEM 亮度更新。

   现在在原显示线程排队重算，合并重复请求。重算期间再次请求不会递归或形成无限自投递，异常后仍可再次请求；旧运行时关闭后待执行任务不更新 OEM。

4. 输出钩子的运行时查找在 `states` 注册表锁内调用 OEM getter；替换运行时也在注册表锁内执行旧实例清理，其中可能取消监听器、恢复设置。

   现在在锁内只取实例快照，随后在锁外查找显示对象或清理旧实例。保留主屏身份与显示线程限制。

5. 正常自动亮度未持有手动节点模式时，原输出判断先查询模块适用用户，再检查所有权。

   现在先检查内存中的所有权、确认状态、暂停状态、屏幕转换状态和租约，再进行必要的有效性检查。普通自动模式直接返回，不访问系统亮度模式。已确认的手动接管仍保留锁屏/交互状态校验，未以缓存放宽指纹安全条件。

## 保留的保护与验证限制

- 原生节点守护仍仅由明确的手动操作启动；自动模式不启动、不新增节点写入。
- 手动输出在屏幕切换回调中立即停止 Java 拦截；原生暂停租约在清理任务执行时写入，存在一个消息队列交接窗口。原有节点为零时禁止写入、首个正亮度由系统处理、锁屏禁止接管、租约超时退让均保留。须用真机验证 DOZE/AOD、指纹高亮与节点权限归还的实际时序，宿主测试无法证明硬件无闪烁。
- `getCurrentNit` 中的持久记忆恢复仍需验证当前模型并按既有语义恢复；本轮将其重算排队，没有更改首帧曲线语义。
- 已接管手动节点时的模式/锁屏有效性校验仍可能访问系统服务。本轮未在缺乏故障证据时以陈旧缓存替代校验，未修改相关安全门槛。

## 测试

- `refactor_brightness_control.py`：224 项，新增无所有权息屏不写设置、前置回调在 Settings 读取故障时仍立即返回、重复事件合并、暗光状态延迟清理、快速息屏/亮屏、关闭取消、手动节点即时放行与延迟暂停/恢复。
- `refactor_raw_output.py`：26 项，执行生产输出钩子，覆盖主/副屏、显示线程、首帧与零亮度放行；OEM getter 若在注册表锁内调用就失败。
- `refactor_display_scheduling.py`：22 项，提取实际调度方法，验证请求合并、OEM 反向重入、无递归/无限队列、异常后恢复、队列拒绝、关闭后取消效果、采样发布延迟及线程限制。
- 全量构建结果记录在交付包 `build-info.json`；正式签名沿用已有证书。

## 受影响真机需要验证的场景

1. 保留用户当前配置，确认加载 r12，记录机型、系统与模块开关；重复息屏后指纹盲解，分别有/无 AOD。
2. 暗光锁定关闭/开启并实际进入锁定，各自验证息屏和解锁；在手动面板未开启时先验证，隔离原生节点接管影响。
3. 单独启用手动节点模式，验证息屏暂停、AOD、解锁恢复及切回自动后的权限归还。
4. 若仍卡死，对照停用模块，采集 system_server watchdog/ANR、线程栈、显示服务及指纹日志，区分 Java 锁等待、驱动等待、原生节点争用或其他模块交互。报告必须附精确构建，不能只写“2.4.0”。

实现的排队机制依据 [Android Handler 文档](https://developer.android.com/reference/android/os/Handler#post(java.lang.Runnable))；文档说明投递任务会在 Handler 关联线程的消息队列执行，并不保证设备级故障已修复。
