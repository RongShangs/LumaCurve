# K90PM OTA 核对与传统映射唤醒风险修复

2026-10-10，`internal-2.4.0-r18 / 24018`，内部测试、未发布。

## 对 K80PM 同样出现问题的判断

可以提高“传统物理映射接入及唤醒恢复路径”的排查优先级，尚不能等同于所有传统曲线设备都存在相同适配故障。K90PM 故障包已经确认 `physical_mapping`；K80PM 当前只有类似症状反馈，缺少其运行后端与故障栈。两类后端还共享场景、温控、状态写入和输出钩子，单凭机型或症状无法排除共用路径。

## 确认的恢复调用风险与 r18 改动

固件中的正常映射 `getBrightness(float,String,int)` 读取当前样条，转换为 framework brightness；`resetShortTermModel()` 先调用映射的 `clearUserDataPoints()`，再重置外层短期模型。模块在内层 getter 前同步调用 `maybeRestore()`，或在内层 clear 后立即处理恢复通知，会把模型修改、系统服务读取带入尚未结束的 OEM 调用。

恢复本身通过 `resetShortTermModel()` / `setScreenBrightnessByUser()` 清理并重建映射。原实现有 replaying 和取消待恢复的保护，不能据此直接断言发生无限递归；但在 getter 中修改正在读取的模型，以及在外层 reset 完成前处理通知，是可以消除的调用顺序风险。

r18 将这些入口改为在原显示 Handler 排队：

- getter 钩子只请求恢复，等当前 OEM 计算返回后再判断并执行。
- clear/reset 钩子只请求处理通知，外层模型重置返回后再处理；避免内层回调直接访问电源服务或触发记忆保存。
- 有效照度回调也只排队，保留原有亮屏稳定等待与 20 秒期限。
- 合并重复请求；新的手动调整、取消恢复和关闭会移除排队任务。恢复产生的 reset 不再排队回调自己。
- 两种后端共用同样的时序保护；不改曲线、记忆强度、场景默认值、采样率或用户开关。

这些是实际的预防性稳定性修复，尚未得到故障设备线程栈证明与 K90/K80 偶发卡死的因果关系。

## 固件提供的新取证位置

小米 `WatchdogImpl` 的 `saveWatchdogTrace` 额外保存 `watchdog_pid_` / `pre_watchdog_pid_` 文件到 `/data/miuilog/stability/scout/watchdog`，标准框架还保存 `/data/anr/BinderTraces_pid...`。r18 同次导出补收这些文本类记录，沿用最近 72 小时、单文件 8 MiB、数量和总时间限制。只选择明确前缀，不遍历 hprof 目录或收集堆转储。

固件的 Watchdog 原生抓栈目标名单包含 vold；这解释了现场 vold 的 unwind 失败可能出现在系统抓栈阶段，但不能证明本次确由 Watchdog 触发或 vold 导致。

## 验证与当前结论

- OTA 同版本传统映射 ABI/单位/元数据/调用路径：59 项通过。
- 生产记忆持久化及主题回归：168 项通过，包含新增排队、上万次合并、服务读取延后、新手势取消和拒绝排队后的恢复检查。
- 传统接入模型回归：2091 项；诊断回归：91 项，覆盖小米 Watchdog/Binder 文件筛选和排除堆转储。
- 全量构建、原签名与源码/交付差异核对按 r18 记录，不继承 r15 真机验证。

目前应表述为：传统映射的唤醒恢复路径是重点嫌疑，已修复其中可确认的调用时序风险；K80PM 是否同后端、同根因，以及 r18 是否消除卡死，均尚未确认。无需故障用户频繁切设置、主动复现或重复导出；本地分析继续使用已有材料。
