# 3.1.1 Beta 03 复审

## 输入与确认事实

用户回传 Beta 02 分析包，第二光感已有变化的有效样本，但 24 次亮度流水的来源标记均为 0。该固件常量中 0 为 INVALID，1/2 为主 / 辅。蓝色基础计划的 30/600 lux 逻辑值为 75.2211/180.9285，实际 OEM 锚点为 215.7029/352；30 lux 的值精确吻合出厂基准在 1.1475 lux 拖动到 3.572 后的重建公式。

配置、确认和运行 revision 相同，因此保存链路成功；实际锚点未保持设定。旧 active_logical_nit / applied_base_nit 来自 CurvePlan，不能作为字段写入成功的依据。原始默认字段读回缺失，不能单凭该包确定首次写入失败、后续重置或运行优化；mDefNit 字段非 final，不宣称已证明 ART 内联为根因。私有固件、设备包和反汇编均留在忽略的 build 和工作区 diagnostics 内。

## 辅助输入路径

实际 services.jar 的 AutomaticBrightnessController 构造函数在初始化 OEM 实现后调用 supportDualSensorPolicy，并保存 mSupportDualSensorPolicy。后续 updateAmbientLux 依据该缓存决定是否调用 updateDualSensorPolicy。移植系统最初找不到第二传感器时缓存为关闭；仅替换辅助传感器不能更新这份构造期缓存，足以解释有采样而仍走单光感分支的情况。

AssistSensorCompat 先核验缓存、原生能力查询、初始化方法及当前控制器身份，再开始绑定事务。绑定后先验证原生能力查询返回支持，更新本次 ABC 缓存；主光感已经启用且具有有效照度、辅助原本也已启用、来源仍为原生 INVALID 时，仅调用一次原生初始化并传入 ABC 已接受的照度。事件编号和 INVALID 从当前固件常量读取。没有伪造辅助样本或直接指定辅助来源。

停用、用户 / 策略 / ABC 变化时恢复本次修改。原始缓存为真时不擅自关闭；其他组件换入新的辅助对象时不覆盖它。原生对象存在时仍提前退出补位路径。未知身份、单位、签名与候选歧义的保护沿用 Beta 02。

## 曲线保持路径

HookEntry 原先只有 savedBase 非空时才在 resetDefaultSpline 后恢复曲线和覆盖 defaultAtLux，普通蓝色参数编辑漏掉该保护。现统一对当前启用计划处理，同时在实际已观测到的 updateLogicalCurve、setAutoBrightnessState、shouldUseGoodCurve 公共事件后核对。

RefactorAdapter.reconcile 按当前手动点次序分别核对主锚点和备用锚点。沿用原固件段端点混合、单调限制的规则，只有当前数组吻合出厂或实际默认字段采样基准时才校正基础，未知重建结果保留并在诊断中标明未核对通过。OEM 仍管理插入、替换、移除、点数和顺序，模块没有新增手动点。保存下来的多节点基础在可确认的四点默认重置后恢复完整形状。

所有操作在原显示线程、当前用户、配置启用时进行。正常 native 结果不改写；传统物理映射不进入这条修复。失败走现有恢复机制，修复不在光感定时器或每次输出中反复执行。原温控、电量、HDR、映射和输出保护继续运行。

## 验证与限制

新增真实故障数值回归，先复现 215.7029，再验证按用户计划校正且手动点 / 计数 / 顺序不变；覆盖普通基础、字段漂移、重复核对无写入、未知算法不覆盖、无效坐标拒绝、恢复 / 关闭、端点、多段记忆及七点保存基础。辅助回归覆盖构造期缓存、原生初始化、无效或已停用主光感、撤销、对象替换、能力拒绝与异常回滚。原记忆测试的 OEM 双替身补齐有序插入，符合生产接口前提，原有失败回滚断言保留。

专项回归：曲线完整性 49 项、辅助光感 69 项；真实固件静态核对 27 项。全量构建完成，共 85 条 PASS 汇总；传统曲线 2377 项、亮度控制 386 项、独立自检 242 项继续通过，117 份 Java 源文件随包核对。最终签名和交付哈希以 build/beta-3.1.1-beta03/final-audit.json 为准。目标设备没有加载本包的实际记录；静态检查与主机模型不代表设备验证，不保证所有移植包均适配，也没有新增功耗实测结论。
