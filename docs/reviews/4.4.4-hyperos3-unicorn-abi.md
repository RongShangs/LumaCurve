## 问题与样本

- 样本：Xiaomi unicorn / 2206122SC，Android 15，`OS3.0.4.0.VLECNXM`。机型仅作背景，选路依据是设备实际接口，不按机型或系统大版本放行。
- 现象（改动前）：模块自检 `available 18 / unsupported 18 / pending 8 / inactive 1`，8 项因 `NoSuchMethodException` 或 HBM 数据类身份不符整体 `pending`；其中 `thermal`、`control_center_partition`、`node_output` 还牵连下游范围/输出判定。
- 改动后同设备导出（07:52，尚未含第六变体）：`available 25 / unsupported 19 / pending 0 / inactive 1`；`thermal`、`hbm`、`outdoor`、`outdoor_range`、`opr`、`nit_limit`、`control_center_partition` 为 `available`，`node_output` 仍为 `unsupported`（`NoSuchMethodException: BrightnessClamperController.getMaxBrightness []`）。
- 覆盖安装含 `brightness_clamp_cap` 的同一构建后再次导出（08:45，包完整）：`available 26 / unsupported 18 / pending 0 / inactive 1`；45 项逐项比对，唯一变化是 `node_output` `unsupported → available`（detail “实际接口检查通过”），全包无 `getMaxBrightness` 异常。该结果只证明选择器在设备上取到了 `mBrightnessCap`，不证明节点写入已发生。
- 原厂类事实（私有反汇编，不入仓库）：`BrightnessClamperController` 只有 `private float mBrightnessCap`（构造时 `1.0f`）与 `getBrightnessMaxReason()`，**没有** `getMaxBrightness()`；`DisplayPowerControllerImpl.adjustSdrBrightness` 为四参（第 4 参 `BrightnessReason`），五参旧签名不存在；`HighBrightnessModeData` 存在两种数据身份（`display.config.*` 十字段与 `DisplayDeviceConfig$HighBrightnessModeData` 七字段）；`adjustBrightnessByOpr` 在本机为两参 `(float, BrightnessReason)`。
- 未确认部分：`opr` 放宽未实际发生（`opr_envelope_profile=unconfirmed`、`outdoor.active=false reason=scene`）；`thermal` 无 `severity>0` 实景；HBM 时间预算 `hbm_budget_supported=false`。

## 路线契约

| 项 | 内容 |
| --- | --- |
| 功能 ID / 新路线 ID / 父路线内部变体 | `thermal` → `thermal_sdr_signature`；`outdoor`/`outdoor_range`/`opr`/`nit_limit` → `outdoor_sdr_signature`、`opr_signature`；`hbm`/`control_center_partition` → `hbm_data_identity`、`control_center_partition_boundary`；`node_output` → `brightness_clamp_cap`。六条均为既有父路线的 ABI 变体，不新增顶层路线 |
| 负责适配器与选择方法 | `HookEntry`（温控 SDR）、`OutdoorTuning`（户外 SDR）、`OutdoorOpr`（OPR）、`HbmAccess`（HBM 数据身份与 SDR/OPR 选择器）、`ControlCenterPartition`（边界类型）、`OutdoorNodeBridge.clampCap`（钳制上限） |
| 原路线是否原样保留 | 保留。旧五参 `adjustSdrBrightness`、三参 `adjustBrightnessByOpr`、`com.android.server.display.config.HighBrightnessModeData`、公开 `getMaxBrightness()` 都作为回退或首选之一原样保留，不删除、不改名 |
| 完整类、签名、字段类型、静态性、对象及数据形状 | SDR：新 `(float,float,boolean,BrightnessReason,boolean)`，旧 `(...,boolean,boolean)`；OPR：新 `(float,float,BrightnessReason)`，旧 `(float,float,float,BrightnessReason)`；HBM：`display.config.HighBrightnessModeData` 十字段或 `DisplayDeviceConfig$HighBrightnessModeData` 七字段（`minimumLux/transitionPoint/minimumHdrPercentOfScreen` 为 float，`time*` 为 long，`allowInLowPowerMode` 为 boolean，后两字段存在性可选）；边界：非静态 getter 返回 `public float transitionPoint`；钳制上限：`mBrightnessCap` 为实例 float 字段，或旧 `getMaxBrightness()` 返回 `public float` |
| 优先接口存在但残缺时的拒绝规则 | 字段存在但类型不符 → `NoSuchFieldException("mBrightnessCap type")`，不用旧访问器掩盖；HBM 未知实例字段或字段类型不符 → 拒绝克隆/校验；边界 getter 返回类型不符 → 拒绝；SDR/OPR 只有“完整新签名缺失”才回退，参数个数或类型半匹配不回退 |
| 与其他路线互斥 / 合作、进入顺序 | 与曲线后端互斥无关；`refactor` 路线仍先探测，缺失则回退 `physical_mapping`（本机命中，属预期）；温控、户外、OPR、节点四条各自独立安装，节点仍需户外/范围/HBM 全部满足才写入 |
| 调用线程、主屏、用户、控制权和坐标单位 | 全部在显示线程内判定；节点写入判定要求主屏、当前用户、`onDisplayThread`、屏幕亮且交互；控制权 `none` 且自动/解锁；坐标继续使用框架实际比例（`ddc_hbm_transition`），不换算 nit |
| HDR / 温控 / 电量 / HBM / 手动接管保护 | 节点写入要求 `hdrActive()==FALSE`、`thermalSeverity==0`、温度 ≤ min(43, ceiling)、电量 ≥30；OPR/SDR 只放宽既有策略，不接管手动亮度；HBM 预算不可用时保留系统零计时 |
| 配置原值 / 本次运行副本 / 升级迁移 | 不新增配置键；变体只影响运行时选择。HBM 副本按实际字段类型构造，未知字段不复制；升级不需要迁移已保存值 |
| 状态证据与未确认 / 未就绪的表述 | 自检仅承诺“实际接口检查通过”；`hbm` 明确写“本机未启用 HBM 时间预算”；`opr` 记 `unconfirmed`；`oem_v1_ready=false`（`RefactorBrightnessUtil` 缺失）不写成路线可用 |
| 安装失败、运行异常、停用、对象替换的清理 | 选择器在安装期一次性解析；失败按 `FeatureSelfCheck` 隔离为 unsupported/pending，不牵连其他功能；节点写入异常置 `failed` 并释放租约；无新增静态状态 |
| 是否新增监听、工作线程、进程或定时工作 | 无新增监听/线程/进程/定时；复用既有 `HyperLux-outdoor-lease` 单线程与 500ms 复检 |
