# 曲线保存后目标响应过慢修复

截图中前置照度为 0.9 lux，自定义曲线约 60%，但实际目标为 6.9%。
仅凭截图不能确认设备写入是否成功，也不能确认是否被系统自动亮度覆盖。

在完整生产主循环的受控 I/O 测试中已复现以下问题：
前后光感分别保持 0.9 / 11 lux，NDK 按变化上报，运行稳定后保存 60% 曲线。
旧路径把修改曲线也交给环境目标防抖处理，暗处每步最多提高最大背光的
1.2%，每步等待约 3 秒，加上轮询间隔约 4 秒才前进一次。
修改后第 16 秒的目标仍只有 820/16383（约 5%），大幅编辑曲线可能需要几分钟。
这证明了目标响应过慢，不能据此声称所有实机问题都由这个原因引起。

修复：有效配置重载时，只有启用状态或实际使用的自定义锚点发生变化，
才清除一次目标防抖初始化。下一次控制计算采用经保护限制的新目标，
执行器继续平滑过渡。温控、低电量、传感器保持、唤醒保护、所有权判断
仍在原路径中执行。相同曲线重复重载、无效配置回滚不会清除防抖。

验证：

- 完整主循环，静止 on-change 双光感，默认曲线改为 60%：约 1 秒后目标 9830/16383。
- 同条件从 60% 曲线改为 0.1%：约 1 秒后目标 16/16383。
- 70℃可信温度下改为 100%：目标限制为 3277/16383（20%）。
- 三例均执行真实生产执行器代码，并在模拟背光文件上发生写入。
- 第四例注入 25ms 传感器 I/O 延迟，更新事件正常进入控制链路，保持标志为 0。
  移除采样后控制时钟更新，完整主循环重新出现错误保持，负向测试通过。
- 配置单元测试覆盖相同曲线重载不重置、无效配置不重置；删除修复会触发断言失败。
- 既有 37 个基线、38 个默认时域、12 个双光感、7 个学习/曲线主循环场景继续通过。

以上为本地主机受控模拟验证，尚未对用户实机验证。
设备诊断应结合 brightness_owner、daemon_can_write、write_governor_reason、
last_write_result、last_write_readback、write_readback_mismatch_streak，以及目标和当前背光。
运行中或过渡中等界面标签不能单独证明写入成功。

## 实机反馈追加

用户提供的状态明确显示曲线已加载，`sensor_hold_active=1`、
`write_governor_reason=sensor_hold`，使最终目标等于当前亮度。
前置样本年龄为 0，而选中照度年龄约 58 秒。
主循环在采样前取时，采样函数使用真实到达时刻，数毫秒 I/O 延迟可能使
新样本被 freshness 检查拒绝为未来时间。本次在四处采样后更新控制时钟，
保留原始样本时间、次数和已有 on-change 有效性规则。

同一反馈的 `last_write_result=-1` 表示写入失败，但不包含 errno，
尚不能确认权限、SELinux、节点不可写或其他设备原因。
本次在真实 Android libc 边界补充 open/write/短写/close 错误日志：
中文失败信息、阶段、errno 和系统错误原因，相同错误每 10 秒最多一次。
保留原 syscall 返回值和 errno，不添加宽泛权限策略或改变安全模式。
受控测试验证四个错误阶段、重复错误限频、无关文件不报错及 errno 保留。
仍需新包实机日志确认写入失败的具体原因。
