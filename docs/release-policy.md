# 发布约定

当前 APK 主线不能使用旧 C/KSU 发布脚本。工作区保留的 `.github/workflows/release.yml` 原先被 Git 忽略，本轮改为手动历史检查并移除发布权限；新 `compatibility.yml` 仅设计为只读维护检查。正式发布时 GitHub 因当前 OAuth 凭据缺少 workflow scope 拒绝新增工作流，因此两份工作流仅保留本地，未纳入发布提交或源码 ZIP，远端 CI 尚未启用；本轮已完成的维护契约与完整回归由本地检查记录提供。当前发布仍按完整 APK 交付流程执行，不能用打标签代替验证。

感谢名单由 `website/thanks.json` 维护，网站和 APP 共用；本地预览脚本由构建、网站同步工具生成；随包离线名单仅在明确需要时另行更新，日常增补只改网站名单。

感谢名单的增删或留言修改不写入版本更新日志、Release 更新说明和官网版本更新摘要。需要展示名单时更新名单本身及 README 的感谢名单区即可。

## Beta 更新日志

每个 Beta 的更新日志都以它开始时**上一个已公开发布的正式版**为基线，累计该正式版之后至本 Beta 的全部更新，不能只写相对前一个 Beta 的差异。基线必须明确标注；不能按版本号猜测正式版已经发布。

每个 Beta 保留独立的版本文件、版本名称、versionCode 和构建标识；累计日志内按 Beta 01、Beta 02 等分别分段，说明各项变化在哪一版引入或修正，不合并成无法区分版本的一份说明。新 Beta 的文件包含此前相关 Beta 的分段；旧 Beta 的文件不能写入后来才有的变化。已合入基线正式版的内容不重复计入。

当前 4.0.2 Beta 01—08 的累计基线均为已公开的 **4.0.2 / 40200**。后续正式版实际发布后，新 Beta 再切换到新的正式基线。发布渠道和随包说明采用对应 Beta 的累计日志；已经交付的 APK / ZIP 作为历史快照保留，不因单独整理文档而静默重打包。

## 交付核对

发布前核对 APK、版本代码、构建标识、源码包、恢复包、网站下载与更新元数据一致。发布说明区分本地测试、固件接口核对与实机验证，不将静态检查表述为实机适配通过。

后续正式发布必须同时更新官网，不能只推 GitHub / LSPosed。官网文案、版本号 / versionCode、APK、对应源码、完整包、SHA-256、update.json 与 update.js 必须与实际发布一致，逐平台下载核对后才标为发布完成。本地打包只准备本地网站和部署包，不上传、不提前变更线上下载或版本元数据。

## 正式版说明分层

从 4.1.0 起，正式更新说明顶部先用简短清楚的用户语言说明新增功能、适配设备和体验改善，不堆具体技术名词；下方再提供完整变更、兼容路线与验证边界。4.1.0 合并公开 4.0.2 后 Beta 01—08 的最终结果。后续 Beta 累计基线在正式发布完成后切换到 4.1.0 / 41000。

## 同版本修订

用户明确要求不抬版本号重新发布时，保留版本名称和versionCode，使用递增的构建修订（如release-4.1.0-r1）及独立dist目录；已有APK/ZIP不覆盖。官网同步与网站打包通过--release-dir指定已验证的新目录，公开资产更新到新包。公开日志说明同版本需手动覆盖下载，不能假称原用户会收到新版本提醒。源代码标签与分发仓库标签同步指向修订提交，保留旧提交与私有校验快照。
