# HyperLux 2.3.1-beta02

此测试方案已由 beta03 取代：用户确认面板问题来自临时 Root 的 sysfs 写入限制，beta03 撤回了本文中的 MediaTek 输出通道，保留独立的暗光修复。以下是当时测试方案的历史记录。

本地测试版，尚未发布。沿用 2.3.0 的包名、签名及配置格式，可覆盖安装；安装后需重启手机，使 Android 系统进程重新加载 Hook。

## 本轮修复

- 暗光定时锁定：从系统亮度控制器取出实际使用的 SensorManager，按传感器类型和硬件 handle 匹配事件。解决注册成功但不同 Sensor 实例导致回调被丢弃、暗光计时无法开始的问题。设备换光感或管理器时释放旧监听、重新计时。
- 暗光小幅升亮：修复 HBM 数据查询使用仅查找公开方法的反射方式，而固件方法受保护，导致暗光变化阈值设置被静默跳过的问题。保留 HBM/HDR、其他显示和非适用场景的边界；接口异常会记录原因。
- 辅助光感为零：新鲜且有效、覆盖至少一秒的零值历史可以参与有限时长的暗光确认。无效、过期、明显环境变亮或确认时间结束仍放行，不会据此无限锁住亮度。
- 主屏手动面板：保留 beta01 的主屏节点自动识别。对识别出的 MediaTek `mtk-leds` 显示节点，改用主屏末端显示输出通道，把全范围目标交给系统的 PhotonicModulator、DisplayBlanker 和显示 HAL；原生守护只验证会话和租约，不反复写 LED 请求文件。其他背光节点继续使用持有句柄的直接写入路径。
- 面板锁屏、OFF/DOZE/AOD 时暂停，解锁后恢复手动目标；重新开启自动亮度后结束保持。仅用户手动接管会启用该通道，自动亮度不新增常驻原生写入进程。

## 为什么更换 MTK 通道

反馈包中，`lcd-backlight/brightness` 有 105 次成功写入并读回，但用户观察屏幕没有改变。文件值成功不能证明面板物理亮度成功。本轮直接检查了该设备的框架字节码：主屏末端输出最终进入显示 HAL/SurfaceControl 或 LogicalLight 分支，因此补充这条输出通道。不能仅凭现有记录断言具体驱动中哪一段忽略了 LED 文件写入。

滑条单位仍是节点范围对应的代码值，不是 nit；MTK 面板中的“节点缓存”不作为物理亮度验证。系统的全范围映射可以超出普通滑条的限制，但最终亮度仍由设备、驱动和硬件决定。

## 实机测试

1. 安装 beta02，保留 LSPosed 的 Android 系统作用域并重启。
2. 开启暗光定时锁定。主辅光感和系统确认照度均低于设置的进入阈值时，设置页应显示“暗光计时中”，时间归零后关闭自动亮度并保持。持续超过退出阈值后恢复自动；锁屏退出。
3. 暗光阈值开启时，导出分析包，核对 `low_light_threshold_adjustments` 增加、`threshold_error` 为空；短暂小幅主光感变化应减少触发升亮。
4. 给 beta01 无效的用户：打开主屏面板，在低值、中值和高值间滑动，观察屏幕实际变化。导出包中的 `raw_output_backend` 应为 `framework_main_bridge`；不能用 LED 文件值代替实际观察。
5. 面板接管后测试锁屏、AOD、解锁，以及系统重新打开自动亮度；前两者应暂停，解锁恢复，重新打开自动亮度后滑条停止保持。

## 验证边界

本地已增加针对 Sensor 对象身份、管理器切换、受保护 HBM 方法、有效零值辅助证据和主屏全范围输出的回归检查，并核对实际用户固件中的接口及调用路径。主机回调模型与固件静态检查不能替代新通道的实机显示验证。本测试版等待用户反馈，不更新官网、不推送 GitHub、不创建 Release。
