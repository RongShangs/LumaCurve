# HyperLux 2.3.0-test03：直接节点控制修正

本地测试版，未推送 GitHub、官网或正式 Release。

## 对照来源与确定问题

对照 RongShangs/bright 的 GitHub master 中 BrightnessManager.kt 和 watchdog.c：面板经 Root 队列调用独立 C 程序，直接操作 panel1 的 brightness / max_brightness，不使用主屏框架的浮点范围。背屏程序没有关闭主屏自动亮度这一步，也不能把其背屏常亮、主动唤醒路径复制到主屏。

test02 的主屏 raw_begin 原本调用框架 available()。当 HBM 的 brightnessMaximum 超过 1，或 BrightnessInfo 暂时为空时，即使主屏节点正常，也会提前拒绝操作。已用真实控制器的服务替身复现失败，再修改并通过回归。本次修复不依赖这些浮点数据；暗光锁定和旧框架路径仍保持原有检查。

用户仅报告“没有生效、自动亮度没关闭”，尚无其手机的原生错误输出，因此上述问题不是已经确认的唯一实机根因。冻结分组、Root 执行或系统确认失败仍可能阻止接管。

## 本次修正

- 主屏节点模式按设备 max_brightness 设置整数，不按框架的普通亮度范围裁切。
- 自动模式关闭确认后再 ARM / SET；未确认关闭时不写节点。
- 明确报告启动原生守护、关闭自动亮度、传递许可、节点写入和读回各阶段的失败。
- 原生启动退出码、errno 与阶段输出到私有日志；分析包加入 last-panel-error.txt。
- 错误保留在面板并可点击查看，不被每秒状态刷新覆盖。状态查询失败不反复弹窗。
- 保留息屏广播、OFF/DOZE 显示事件与失去交互的退让。关闭弹窗保持；重新亮屏不自动重新接管。

## 安装与验证

覆盖安装同签名 APK 后重启一次，设置保存并应用，然后从磁贴打开主屏弹窗。先试中等节点值和整数输入，观察系统自动亮度是否关闭、节点目标与实际是否一致。关闭弹窗保持，再打开自动亮度、锁屏与进入 AOD，确认停止守护并恢复节点权限。

如果未生效，失败弹窗可选择文本；日志页导出的分析包包括本次操作阶段、主屏实际值、原生启动记录和系统 ACK。无需重复运行外部探测脚本。

已验证生产控制器、Root 操作编排的成功和失败退让、ARM64 编译、既有回归与签名。无连接的 Android 设备，尚未做实机验证。节点数值不是 nit，真实激发亮度与高亮能力由驱动决定。主屏路线不改变 AOD 开关或息屏超时、不主动唤醒。

恢复工具在完整包中：Root 终端运行 sh ./restore_refactor_hook_android.sh；脚本与辅助 JAR 保持同一目录。
