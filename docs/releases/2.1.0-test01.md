# HyperLux 2.1.0-test01：户外亮度链路研究与测试

本地构建 `test-2.1.0-outdoor01`，2026-10-04。未发布，新增效果尚未实机验证；正式版仍为 2.0.4。

## 目标与链路

解决室外强光下曲线目标偏低、软件可用范围限制或自动 HBM 触发/预算不足的问题。继续使用系统光感融合、场景识别、设备映射、动画与硬件输出。

系统主辅光感 → 系统融合与场景 → 当前设备曲线和手动记忆 → **户外目标修正** → **可选软件高亮范围** → 画面、电池、温控及其他限亮 → 系统动画 → 面板。

软件可改变目标和允许范围，不能制造面板不存在的亮度。亮度坐标 1.0 是本机映射上限，不是固定 nit，也不等同于厂商宣传的局部峰值。显示内容、面积、HDR、温度及驱动仍会影响实际输出。没有伪造照度、清空 HBM 历史、写 sysfs 或引入独立 daemon/broker。

## HyperOS 4 固件研究

核对三份本地固件，包含 Refactor 与传统物理映射设备。原固件及反汇编只留在本地。

1. `AutomaticBrightnessControllerImpl.getOverrideLimitBrightness(float, boolean, float)` 位于系统曲线和手动策略之后、自动目标 clamp 之前。户外目标在此加入，不写基础曲线或手动记忆。
2. `HighBrightnessModeController.getCurrentBrightnessMax()` 同时受到 HBM 条件和小米峰值选择影响。单改曲线仍可能被这里压回去。
3. 小米 `BrightnessRangeControllerImpl` 还有独立的照度动态范围：可绕过 HBM getter 直接返回 `mMaxBrightness`，由照度→nit 样条和本机映射计算。本轮把这个已验证的软件范围入口纳入可选控制。
4. 后续 `adjustSdrBrightness` 继续经过 OPR/画面、BCBC、省电、峰值、显示温控和电池限亮。最终 clamper 单独只读，不整体绕过；驱动限制保留。
5. HBM 数据使用十参数构造函数。复制全部字段，只修改副本的 `minimumLux` 和 `timeMaxMillis`，保留 HDR 样条、刷新率等引用，不改变共享的 DisplayDeviceConfig 原对象。
6. 部分设备未启用标准 HBM 计时。此时自动状态字段可能不更新，零预算不能按无限处理。目标增强和软件范围可单独工作，但 HBM 参数调整关闭。
7. 小米显示状态暂停值为 3，可能同时保留自动亮度标志为 true。读取 `mIsAutoBrightnessOffByState` 判断，避免照搬 AOSP 的枚举假设。
8. 系统重新初始化/更新后替换 HBM 数据对象时，采纳新的基准。关闭功能只恢复仍由本应用持有的副本，避免旧对象覆盖系统新配置。固件及曲线身份验证继续保留。

接口和调用顺序核对不能证明所有系统分支、HAL 或驱动都允许更亮。未知接口关闭对应控制，分析包记录实际能力。

## 参数

| 参数 | 默认 | 范围 | 含义 |
|---|---:|---:|---|
| 户外增强 | 关闭 | 开/关 | 确认持续强光后增加目标 |
| 进入照度 | 10000 lux | 2000–50000 | 系统确认后的环境照度 |
| 全强度照度 | 30000 lux | 4000–100000 | 必须高于进入照度 |
| 进入确认 | 3 秒 | 0.5–10 秒 | 过滤短暂照射 |
| 退出确认 | 5 秒 | 1–15 秒 | 过滤短暂遮挡 |
| 退出照度比例 | 65% | 40–90% | 与进入条件形成滞回 |
| 增强强度 | 85% | 10–100% | HBM 分界向可用上限推进比例 |
| 单次最长增强 | 180 秒 | 30–600 秒 | 本应用自己的会话期限 |
| 增强冷却 | 60 秒 | 15–300 秒 | 超时或保护退出后的等待 |
| 自动 HBM 调整 | 关闭 | 开/关 | 仅完整、已启用的计时接口 |
| HBM 照度倍率 | 1× | 0.25–1.5× | 原触发倍率，最低 2000 lux |
| HBM 时间倍率 | 1× | 1–2× | 不超过原时间窗口 |
| 开放软件高亮范围 | 关闭 | 开/关 | 软件峰值与照度动态范围 |

附加开关要求户外增强开启。HBM 参数副本仅在持续强光确认完成后的有效增强期间使用；确认、冷却、手动保持及保护退出阶段恢复系统数据。

目标随照度在 HBM 分界和当前可用上限之间推进，只提高、不压低系统原目标。若 HBM 时间/照度条件不足，仍不能穿过这些限制，APP 展示未满足的条件。

## 交接与恢复

- 显示线程、一次性截止事件；稳定照度不再发事件也会超时退出。进入和退出有不同阈值与确认时间。
- 手动调节优先，直到明显照度变化或熄屏。本应用户外手动保持的离开条件是照度变化至少 5000 lux，且达到当前/原保持照度较大值的 50%；不改写系统自己的记忆机制。
- 屏幕关闭、显示状态暂停、手动模式、HDR/杜比、省电、驾驶/闲置/特殊场景、应用/临时指定亮度、温度未知或超阈值时停止增强。
- 使用已有 38–45℃ 电池温度阈值与 1–3℃ 滞回。严重温控等级停止增强；电池温度不能替代面板温度与驱动保护。
- HBM 预算估值只读历史队列，不调用会裁剪系统历史的方法；缺失就是未知。
- 修改参数保留有效手动保持与冷却；显式关闭清除增强会话，恢复持有的副本并取消事件。
- 运行时异常撤销副本、停止本次增强，不在每帧重复失败；重新应用设置才尝试恢复。
- 配置校验区分目标增强、HBM 调整和软件范围能力，部分不支持不会假称全面解锁。

## APP 与分析包

状态页分支入口及设置页高亮条件展示：照度未达条件、确认、增强、退出确认、冷却、保留手动选择及保护原因。

详细条件分开显示 HBM 分界、原/有效软件范围、照度动态范围、设备映射上限、显示范围、最终 clamper、请求目标与实际屏幕亮度。它们是框架坐标百分比，不是 nit；缺失字段不视为零或关闭。

分析包新增 `outdoor-state.json` 和 `outdoor-limit-trace.json`。前者包含选项、兼容能力、截止时间、HBM 原/有效参数与预算估值；后者最多 32 条变化记录，含时间、输入/输出及是否降亮，覆盖已取得的 OPR、BCBC、峰值、温控、电池、省电及 SDR 阶段。原 pipeline 将系统手动修正与户外修正分开，避免归因混淆。

记录去重、数量有界，没有新增常驻辅助进程或高频轮询。新增内存与 CPU 开销待实机量测，不使用旧模块占用数字宣传。

## 验证和体验方法

确定性模型使用生产回调代码，覆盖配置边界、进入/退出、冷却、静止照度超时、手动保持、锁屏、温度滞回、系统数据替换、异常恢复、动态范围、HDR/省电/策略过滤，以及增强后仍经温控和电池限亮。三份固件检查字段类型、签名和调用顺序。准确计数见合集 `build-info.json`。

上述检查不等于实机亮度验证。建议一次完整体验：

1. 覆盖安装并重启，保持新选项关闭，核对旧曲线、手动调节与锁屏行为。
2. 只开启目标增强保存，在稳定室外强光下比较关闭/开启，观察确认、目标和实际输出；核对暗处不进入。
3. 若软件范围限制输出，再单独开启范围选项。只有计时能力完整的设备，再按需小幅调整 HBM 倍率，避免同时全开导致归因困难。
4. 手动降低亮度、锁屏一次、等待最长会话截止，核对不抢用户选择、交接与冷却。若有循环升降，关闭增强保存，导出分析包。

请求目标提高不等于物理 nit 提高。比较物理亮度需保持光照、内容、面积和温度一致，最好用亮度计测量。

## 包与源码

本地合集是 APP，不是 KSU 模块。关闭增强保存保留基础曲线，「停用并恢复」恢复整套修改。也可在合集解压目录执行 `su` 后 `sh ./restore_refactor_hook_android.sh`，使用同目录 helper，路径均为相对路径。

本轮未推送仓库或覆盖网站正式包。源码不含固件、私人采集和签名密钥。私有固件分析脚本 `tools/analyze_outdoor_firmware.py` 可对用户自己的固件运行；本地测试目录 `build/outdoor-research/`。没有私有输入时构建加 `--skip-device-fixtures`，明确标记跳过静态检查，保留运行时验证。
