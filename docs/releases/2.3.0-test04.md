# HyperLux 2.3.0-test04：主屏守护载荷修复

本地测试版本，未推送或发布。

## 已确认的故障

2026-10-06 12:07 分析包记录在“启动主屏原生守护”阶段失败，系统接管 owner=none、auto=true、guard_running=false，主屏节点可读、max_brightness=16383。尚未进入自动模式关闭或节点写入步骤。

对照实际 test03 APK：assets/hyperlux-main-panel 存在，未压缩长度为 2,160,320 字节。安装器只允许 2,097,152 字节，并把超过上限与文件缺失合并成同一个错误。这是确定的打包与载荷读取契约错误，不是用户 Root、LSPosed 权限问题，也不是主屏驱动缺写入能力。

## 修复

- 原生编译时剥离调试符号，减少文件大小，不改变执行逻辑。
- 提取逻辑统一到 NativePanelAsset，最大载荷 4 MiB，流式读取也遵守同一上限。
- 分别识别缺文件、无效长度、超过上限、读取不完整和非 ARM64 ELF。
- 在签名后的最终 APK 上调用生产读取器，验证实际解压数据与 SHA-256；不再只验证 ZIP 中有这个文件。
- 增加与本次故障同等长度、最大边界、超限、缺文件和错误 ELF 的回归测试。
- 息屏、DOZE/AOD、自动亮度恢复的退让机制和直接节点调节逻辑保持原有设计。

## 测试

覆盖安装后重启一次，设置保存并应用。磁贴打开主屏弹窗，先选择中等节点值，观察系统自动亮度关闭、实际值与目标值；再验证关闭弹窗保持、打开自动亮度退让、锁屏与 AOD。

本地通过生产载荷读取、Root 操作编排、亮度控制回归、原生策略与固件静态检查、APK 签名及源码一致性校验。未连接 Android 设备，后续原生启动和实机背光表现仍需手机验证。

如出现新的报错，失败弹窗和分析包会给出后续步骤的原因。完整包附恢复工具，Root 终端在解压目录运行 sh ./restore_refactor_hook_android.sh。
