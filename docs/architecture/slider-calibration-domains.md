# 控制中心映射的标定有效域

## 原因与分工

原coordinate_v2路线对0至1全域采样并要求严格单调，用于可靠双向坐标转换。原生DisplayDeviceConfig的最低标定亮度可能大于0；系统样条把更低输入裁剪到同一端点。因此全域存在正确但无法一一反解的外侧平台，这不代表主屏节点输出或亮度引擎不兼容。

ControlCenterCalibration集中负责选择与证明，ControlCenterCurve仅承载严格单调有效域和JSON传输。ControlCenterEngine异步发布标定及状态。Root与SystemUI仍消费同一代次/用户/revision绑定，不添加另一套机型判断，不改变自动亮度或节点输出所有权。

## 路线优先顺序

1. 继续尝试原全域严格采样；成功时不增加字段或样条探测要求。
2. 仅严格采样确认平段后，允许追加coordinate_v2_calibrated。要求实际DisplayDeviceConfig的亮度/背光数组完整严格单调，原生正反样条为已验证的LinearSpline或MonotoneCubicSpline，数组与样条一致，纯转换在节点处一致，外侧确实按端点裁剪。
3. 仅在真实标定输入域内采样。内部仍严格单调；中间平台、逆向、非数值、精度不足均拒绝。不推断更高硬件上限，也不伪造最低端为0。
4. Refactor逻辑路线独立尝试原全域。需要新域时，进一步验证实际101项原生逻辑表与两种纯换算，取逻辑表与物理nit标定的有效交集。101来自已核对消费者的100等分协议，不是机型参数。逻辑路线失败只失去V1表，标准坐标路线继续独立。
5. 原生额外低亮度数据生效、结构类型异常、配置/数组/样条/逻辑表在采样中变化时不提交新表。仅这一可选能力等待或暂停，不写回用户设置。

## 数据与生命周期

旧表仍为input/node，保持原解析；新表只在有效域不覆盖0至1时附带range端点，两端必须与input首尾精确一致。严格单调检查保留，缺range的残缺域不接收。输入和输出位于有效域外时使用原生端点，不扩展系统允许的亮度区间。原Root进程、用户、代次、配置绑定和暗光锁定所有权协议不变。

引擎状态新增calibration_profile、compatibility_state、oem_v1_ready与oem_v1_detail；兼容页区分coordinate_v2和coordinate_v2_calibrated。明确无法换算/接口缺失报告unsupported，不再一直写等待；对象尚未就绪等情况仍pending，恢复后可重检。标定失败清理旧转换表，但所有已保存选项保留。

## 验证

新增tests/refactor_control_center_calibration.py执行生产标定、表读写及异步引擎，覆盖多种上下端平台、旧全域路径、内部错误、额外低亮度、逻辑表残缺/反解异常、失效撤表及恢复。原控制中心154项、暗光锁定532项、配置保留2751项继续回归。私有样本9节点回放使用实际硬件坐标和合成框架；Refactor表为协议模型，不宣称执行了设备固件。完整检查通过与否见专项复审和构建回执。

没有新增传感器、轮询、节点守护或Root写入动作；只有现有后台标定线程读取纯转换。没有本轮Android真机或功耗测试。

## 设置呈现与草稿分离（2026-10-28）

ControlCenterSettings是独立设置卡片，ControlCenterStatus是无I/O的呈现模型。换算ready只代表引擎一侧，不伪造系统界面确认。用户草稿与已保存模式分别读取；能力暂缺不回写设置，允许保留既有选择或关闭。重新检测复用现有自检，保存仍经统一配置验证。界面不再保留选择弹窗，搜索定位到卡片标题，所有选项和工具按钮使用自然高度。
