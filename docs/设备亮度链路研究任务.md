# 给手机 root Agent：研究本机的真实亮度链路

目标：弄清楚 HyperOS 在这台设备上如何控制主屏，以及 LumaCurve 写入和系统
控制如何交互。此次不安装新核心、不重写守护脚本、不更改 SELinux、不操作背屏。
当前保持 test03；线性过渡修改尚未合入，避免一边改实现一边测旧问题。

## 已验证与尚未验证

已验证：旧核心把主屏设 0444 后重开失败；0644 下可写；预先持有 FD 可以跨
chmod 写入；test03 实机 124/124 写入成功并读回一致，日志出现目标=实际=4093/1282。

尚未验证：系统是否持续覆盖；为什么约 30% 可以保持而 60% 不行；人眼看到的
跳变对应哪层；sysfs 请求值、实际面板输出与系统亮度 float/nits 的映射。
不能把 max_brightness=16383 当成当前条件下允许达到的亮度，更不能推断达到它
就有相应实际 nit。无测光设备时只能证明数字读回和用户观感，不宣称测得绝对 nit。

## 0. 保存现场与元数据

记录机型、Android API、HyperOS 完整版本、kernel、SELinux、模块构建、PID，
系统 mode/brightness/auto_adj、暂停标志、运行配置、学习记录、曲线预设。
区分 /data/adb/modules 中默认配置与 /data/local/tmp 中实际运行配置。
所有受控步骤结束恢复原有设置、配置、暂停/运行状态；不要删除原日志。

记录主屏 brightness 的 realpath、mode/uid/gid、max_brightness、actual_brightness
（若不存在明确标缺）、bl_power、相关面板只读状态。只列出背屏，不写 panel1。

## 1. 找出系统走哪条通道（只读）

保存 dumpsys display、power、SurfaceFlinger、cmd display help、service list、ps。
优先找主屏 logicalId=0 对应 physical display/port/uniqueId，不混入背屏数据。
从 dump 中找 BacklightAdapter/useSurfaceControl、当前/目标亮度、SDR/HDR、
brightnessMinimum/Maximum、HBM transition point/mode、thermal/power throttling、
reason、RampAnimator/动画速率、temporary brightness、自动亮度控制器。
字段可能因厂商改名或裁剪；找不到就标“未暴露”，不要猜测。

读取实际存在的 /vendor/etc/displayconfig、/product/etc/displayconfig、
/odm/etc/displayconfig、/system_ext/etc/displayconfig 配置，记录选用文件与对应屏幕。
找 brightness/backlight/nits 映射、普通亮度上限、HBM 门槛、thermal 限制和渐变速率。
查看 VINTF 中 composer/lights HAL 版本与对应进程；只有配置不能证明运行时选用，
需和 dump 中的 physical display/config 关联。

检查 system_server、SurfaceFlinger、composer/lights/display HAL 进程是否已经持有
主屏 brightness FD；记录 /proc/PID/fd 和 fdinfo 的路径/flags。没有 FD 不能排除
DRM/ioctl/厂商服务，也不能证明没有写入。不要暂停、杀死或注入这些系统进程。

## 2. 四组对照：保持同一环境、画面、屏幕状态

避免 HDR 内容、屏幕闪烁测试、锁屏、滑块操作、充电状态变化和方向变化。
先恢复温和曲线，不再直接要求 60% 或 100%。每阶段记录温度、电量、充电状态。
阶段之间明确记录操作和时间，采集期间不触碰滑块。

| 阶段 | 模块 | 系统模式 | 要回答的问题 |
| --- | --- | --- | --- |
| A | 暂停 | 自动 | 系统自身是否变化；系统 float/nits 如何对应 sysfs |
| B | 暂停 | 手动 | 系统低/中亮度位置如何映射；系统自身渐变是否平滑 |
| C | 暂停 | 手动 | 小幅原始 sysfs 写入是否落地、被钳制或自动覆盖 |
| D | test03 运行 | 自动 | 模块写入后多久被改；发生覆盖时系统 reason/目标是什么 |

A、B 每组 30～60 秒，B 使用用户认可的两个温和滑块位置，不猜系统整数范围。
设置修改只用系统 UI 或已经核实存在的命令，不猜 SurfaceFlinger Binder transaction。

C 先确认暂停后主屏为 0644，仅写当前值，再最多改变 max_brightness 的 1%，
且不要提高到超过已确认可稳定的温和亮度；立即及 0.1/0.5/1/2 秒读回。
如果已有实际亮度读数，同时记录；不能拿“写入成功”替代“输出确实改变”。
测试后恢复原值。若需观察渐变，最多用同一 1% 区间的 2 秒小幅多步变化，
每次在 0644 下重新打开节点以重置偏移，不要复用 shell FD 连续写而不重置偏移。

D 先固定一个已可达到的温和曲线，稳定后只做一次较小曲线修改，记录保存/重载时间。
连续采集 60 秒，不切模式、不锁屏、不动滑块。对比模块目标、实际 sysfs、系统
目标/动画、errno/readback、external_sync 与保护状态；分别标明升亮/降亮。

可使用配套只读采集脚本，放在手机当前目录，执行：

```sh
sh ./probe_display_android.sh auto_idle 30
sh ./probe_display_android.sh manual_idle 30
sh ./probe_display_android.sh module_auto 60
```

脚本不切模式、不暂停模块、不写亮度；需按阶段先准备正确状态。
记录约 10Hz 的 sysfs 和约 1Hz 的已有模块状态，前后保存系统 dump。
采样实际间隔以 uptime 为准，设置读取与 dumpsys 不在每帧运行。
这会产生临时采集负载，不用于验证模块正式 CPU 占用。

## 3. 分辨“60% 达不到”

必须区分：曲线百分比、模块背光目标、sysfs/max 比例、系统 normalized brightness、
框架估算 nit、实测亮度。不要把它们当成同一线性刻度。

- 写返回失败：查 errno、权限和 FD，属于通道故障。
- 写成功但立即读回较低：查驱动钳制或同步覆盖。
- 立即读回一致，随后变化：查系统/厂商重新写入，而非直接认定硬件上限。
- 读回稳定但观感不对应：查映射、实际输出/HDR/SDR、调光策略；没有测光设备则保留未知。
- 系统 dump 报告 maximum/thermal/HBM 限制：记录实际约束及 reason，再判断是否相关。

不必强行再次测试 60%。先从运行时上限和上述小幅对照判断，保留系统保护。

## 4. 分辨“瞬间变化”

把每帧或约 100ms 的 brightness/actual_brightness 与模块状态放在同一时间轴：

- 原始节点是多步变化，系统/实际输出出现大跳：定位厂商或驱动层。
- 原始节点本身单次大跳：区分模块写入、系统写入、所有权切换和配置重载。
- 原始节点平滑、用户仍觉得跳：考虑感知映射和低亮度相对步长，不能以整数线性
  冒充人眼感知线性。
- 仅 WebUI 数值跳：先排除约 1 秒刷新与旧状态发布造成的显示跳变。

如设备已有可用的 tracing 能力，可用独立实例短时跟踪已确认的相关函数，记录
PID/comm、目标值及时间，结束恢复。不要全局开所有 ftrace 事件，不盲猜内核函数，
不要为此修改 SELinux、停止显示服务或覆盖原有 tracing 会话。
没有跟踪工具时仍可做时序对照，但不要声称已找到了具体写入者。

## 5. 返回交付

1. 元数据、对应主屏的关键系统 dump/config、采集目录与完整原始日志。
2. 四组对照表：系统 mode、模块 owner、当前/目标、读回、errno、改变延迟、系统 reason。
3. 已验证的控制链路图，每条边写证据；推测用虚线，不用“应该”代替结果。
4. 对 60% 和跳变分别给“已定位 / 缩小范围 / 未定位”，列出证据与缺口。
5. 确認现场恢复，test03 构建及暂停/运行状态一致。

暂不做原版和新版同时运行的 A/B。若后续比较原版，须隔离配置、单进程运行、
相同环境和相同温和目标，实际记录写入；不能仅凭算法输出或仿真 exact match 判生效。
